# 2. Web Search and Opportunity Report

## Goal

Add source-traceable web discovery to the prototype without making Tavily mandatory or spending search credits automatically. Users control when a keyword search or full opportunity report is launched.

The implementation reuses the teammate research under `InWebsearchfeature/`, especially its useful ideas:

- Keep title, URL, date, content, provider score, and query.
- Separate keyword, numeric, historical, adoption, investment, proof, and risk searches.
- Enforce query/result budgets.
- Research one opportunity deeply only when the user requests it.

## Diagnosis of the 20-Article Test

The stored run events show:

```text
20 articles selected
4 batches estimated
Batch 1 completed: 5 articles
Batch 2 completed: 5 articles
Application stopped before batches 3 and 4
```

The first two batches accepted 8 articles and ignored 2. The AI did receive article titles and feed content. The provider logs appeared dominated by the company PDF because the same processed company summary was included near the beginning of each batch prompt, before the article records. It was not a PDF-only run and not caused by the system already seeing all 20 articles.

To prevent confusion, batch progress now lists every article title being processed. Company context remains bounded by the Company workspace character/document limits.

## Provider Contract

Both Tavily and SearXNG return this normalized structure:

```text
query
provider
engine
rank
title
url
published_at
retrieved_at
content
provider_score
```

No publication date is invented. Missing dates remain blank.

## Tavily

Tavily uses `https://api.tavily.com/search` and supports `basic` or `advanced` depth. The key comes from `TAVILY_API_KEY` or browser session state and is not stored in SQLite.

The current limits are user-configurable:

- Maximum queries per action
- Maximum results per query

Keyword search uses one query. A full report uses at most the configured query limit.

## SearXNG

SearXNG uses:

```text
GET <base_url>/search?q=<query>&format=json
```

It returns source URLs. It can also return `publishedDate`, but this depends on the underlying search engine. It commonly returns:

- Title
- URL
- Snippet/content
- Engine
- Category
- Optional publication date

The configured local test URL is:

```text
http://100.70.65.86:8888
```

This Tailscale address only works on authorized devices. Other users must provide their own SearXNG URL or switch to Tavily.

The live probe on 2026-08-21 returned URLs, snippets, query, and engine (`bing`), but no publication dates. The first results were broad rather than highly relevant. This confirms that the adapter works and that search quality depends on the SearXNG instance's enabled engines and query construction.

Public SearXNG instances may rate-limit requests, disable JSON output, log queries, or disappear. They are suitable for experiments, not assumed reliable infrastructure.

The UI now separates:

- `SearXNG local/private`
- `SearXNG public instance`
- `Tavily`

Local and public SearXNG use the same `/search?format=json` contract. Public mode is separate because public instances commonly disable JSON, block automated clients, apply bot protection, return HTML, or rate-limit requests. The compatibility button tests the configured URL before a real research run.

`https://searx.space/` is an instance directory, not a search instance. Choose one of the listed instance base URLs. On 2026-08-21, `https://searx.oloke.xyz` returned HTTP 503 for JSON API requests, so it was temporarily unavailable or blocking API access; the URL format itself was not missing a path.

## Keyword Discovery Flow

```text
User query
→ selected search provider
→ source preview
→ user chooses import
→ results become article records
→ normal bounded triage/extraction/scoring pipeline
```

The original URL and returned date remain attached. Search results are deduplicated by URL within the run and article imports are deduplicated by a URL hash.

## Cookie Walls, Bot Challenges, and Content Hygiene

Search engines sometimes return a source URL with a useless snippet such as `Please Enable Cookies`, `Site verification`, `Enable JavaScript`, `Access denied`, or a bot challenge. Sending that text to the AI wastes context and can make a source appear more informative than it is.

The search layer now assigns one content status:

- `usable`: the search snippet contains enough readable evidence.
- `enriched`: a weak/blocked snippet was replaced by readable text fetched from the source page.
- `thin`: content remains too short after direct fetch.
- `blocked`: cookie, consent, CAPTCHA, verification, access-denied, or bot content remains.

Direct fetching happens only when the search snippet is empty, shorter than 80 characters, or contains a blocked marker. Normal useful snippets do not create an extra network request.

For weak results, the application:

1. Fetches the original URL once with a normal browser user agent.
2. Accepts readable HTML only.
3. Removes scripts, styles, navigation, headers, footers, forms, SVG, and noscript blocks.
4. Prefers `article`, `main`, or common content containers.
5. Rechecks the cleaned text for cookie/bot markers and minimum length.
6. Stores `content_status`, `content_source`, and `extraction_error`.

Blocked and thin records stay visible in search history with their original URL, query, provider, engine, and retrieval time. They are excluded from Signal inbox import and full-report AI context by default. Only `usable` and `enriched` records enter those paths.

Existing search runs can be cleaned using `Recheck and clean preview content`, so a user does not need to spend another Tavily credit or rerun SearXNG.

The tested Orange financial URL returned HTTP 200 but its page title was `Site verification` and its body requested cookies/JavaScript. The application therefore retains the source URL as blocked rather than treating the verification page as financial evidence. It does not attempt to bypass CAPTCHA, bot protection, authentication, or consent controls.

## On-Demand Opportunity Report

Reports are not generated for every opportunity.

The user selects one opportunity and authorizes the report. The process is:

```text
selected opportunity
→ existing evidence
→ company context assigned to full_report/all
→ 1 AI planning call interprets the opportunity and creates bounded research tasks
→ Tavily or SearXNG executes those queries
→ URLs/snippets/dates are retained
→ 1 AI call creates a cited structured report
→ report persists in SQLite
```

Each report stores the exact `search_run_id` that produced its web evidence. Before showing the generated narrative, the UI displays:

- Search provider and AI model
- Search-run start, finish, and status
- Exact queries proposed by the planning AI
- Result count per query
- Usable/enriched and blocked/thin counts per query
- An expandable source table with URL, engine, rank, returned date, retrieval time, and extraction status

Saved reports remain selectable after a Streamlit restart. Reviewing a completed report therefore does not trigger another AI or web-search request.

Nested report values are normalized only for display. Lists and dictionaries, including mixed citations such as `[1, "E2"]`, become JSON strings before Streamlit/PyArrow renders the table. Stored report JSON and citation meaning remain unchanged.

### Research-planning call

The first AI call is not a title-to-keyword shortcut. It receives:

- Full opportunity record and current title
- Vertical, use case, and technology fields separately
- Attractiveness/right-to-win factors and rationales
- Existing evidence claims, dates, signal types, and URLs
- Current evidence domains
- Active-company profile
- Bounded company summaries assigned to `full_report` or `all`

It must return:

- Opportunity interpretation
- Decision questions
- Known evidence
- Evidence gaps
- Naming risks
- Structured research tasks

Each research task includes:

- Purpose
- Unknown to resolve
- Natural search-engine query
- Preferred source types
- Geography
- Freshness requirement
- Explanation of how the answer changes the decision

The planner is instructed not to repeat the full opportunity title in every query. It translates internal or invented naming into terminology likely used by buyers, regulators, analysts, procurement portals, technical teams, competitors, and partners. Python removes duplicate queries and caps their length/count before search.

Python also checks whether the bounded plan covers the report's five expected evidence dimensions:

- Market demand or buying/procurement evidence
- Financial/quantitative evidence
- Regulation and risk
- Named implementation proof
- Company, competitor, partner, and capability fit

The planner remains free to choose the tasks and language. If a dimension is missing and query budget remains, Python adds one concise fallback task for that gap. The report audit displays the final coverage map. This prevents a fluent planning response from silently omitting a required report dimension.

This remains a two-AI-call report flow: one planning call and one synthesis call. No third model call was added.

Expected report fields:

- Executive summary
- Confidence and evidence gaps
- Market estimates with ranges and assumptions
- Company direct/partner roles and capability gaps
- Competitors and partners
- Risk register with likelihood, impact, mitigation, and sources
- Phased roadmap with owners and success metrics
- Financial scenarios with low/high investment and value ranges
- Recommendation
- Next validation steps
- Full source list

Financial values are estimates, not verified forecasts. They must be ranges with assumptions and cited source IDs.

## Visuals

Only two report charts are included because each has a decision purpose:

1. Scenario ceiling comparison: investment versus estimated value.
2. Risk matrix: likelihood versus impact.

The roadmap remains a table because a decorative chart would not improve the decision.

## Company Personalization

`full_report` is available in Company workspace stage assignment. Documents assigned to `all` also remain eligible.

The full report can therefore use selected company summaries for:

- Company vocabulary
- Existing capabilities
- Partner preferences
- Strategic priorities
- Past experience
- Financial or operating context

Raw company documents are still excluded. Only processed, selected, bounded summaries enter the report context.

## Data Tables

### `web_search_settings`

Provider, Tavily depth, SearXNG URL, max queries, and max results.

### `web_search_runs`

Purpose, provider, opportunity, status, query count, result count, and errors.

### `web_search_results`

Normalized source records and optional imported article ID.

### `opportunity_reports`

Opportunity, company, model, provider, exact search-run ID, query/source counts, report JSON, and errors.

## Cost and Safety Rules

- Search never runs automatically when the dashboard opens.
- Keyword results enter the main pipeline only after user import.
- Full reports are user-triggered for one selected opportunity.
- Full reports use at most two AI calls.
- Search query/result limits are visible and configurable.
- Tavily keys are not persisted in SQLite.
- SearXNG missing dates remain blank.
- Search snippets are not described as verified facts.
- Report estimates must identify assumptions and uncertainty.

## What This Must Not Do

- Never generate reports for all opportunities automatically.
- Never hide or remove source URLs.
- Never invent publication dates.
- Never treat provider ranking as evidence quality.
- Never treat a search snippet as confirmed primary evidence.
- Never send unresolved cookie/verification text to the AI article queue or report.
- Never attempt to bypass CAPTCHA, authentication, bot protection, or access controls.
- Never present financial estimates as guaranteed outcomes.
- Never send all raw company documents into report prompts.
- Never spend Tavily credits without explicit user action.
- Never assume the local Tailscale SearXNG URL works for teammates.
